## 1. 候選成因（依「是否為計算錯誤」分類）

### 🟠 H8（中-高｜**資料品質問題、直接影響此症狀**｜loop 11 發現）北外環道路被嚴重低估容量
- **證據（loop 11，查 graphml）**：「**臺南都會區北外環道路**」12 段中 **7 段標為 `tertiary` / 1 車道 / 40km/h**，僅 5 段為 `trunk` / 2 車道 / 70km/h。整體外環道路 31 段更有 23 段是 1 車道、15 段 30km/h。
- **後果**：一條都會區外環道路（現實應為 trunk、每向 2–3 線、60–80km/h）有過半路段被當成 **1 線 40km/h 次要道路** → 容量 `q=u·w·κ/(u+w)` 被**大幅低估**（1線40km/h ≈ 0.6 veh/s vs 2線70 ≈ 1.6）。這些低容量段沿環道形成**瓶頸**（走廊吞吐被最弱段卡住）→ **直接造成/惡化北外環的塞車**。
- **性質**：**不是程式碼 bug**——code 正確使用資料的 lanes/speed；屬**輸入資料**面。
- **⚠ loop 12 軟化（修正 loop 11 過度確信）**：全網查發現 66% 邊是 30km/h、85% 是 1線≤40km/h，且這些**多為 OSM 真實 maxspeed**（台灣地方街道本就 30-40），**非 fallback 假象**；主幹道(trunk/primary/secondary)僅 9% 是 1 線。故**全網低容量大致真實、非系統性低估**。北外環那 7 段 tertiary/40km/h **可能反映該路沿線性質真的改變**（部分穿市區），**未必是標錯**。要斷定 mis-tag 需**地面驗證**（Google Maps/實景比對那 7 段實際幾線/限速）。
- **修法（若地面驗證確為 mis-tag 才做）**：修正北外環各段 lanes/speed 後重建 graphml。屬資料修正，非改 code。
- **與症狀關係（下修）**：H8 **可能**是加成瓶頸，但「確定低估」需地面驗證；**不可在未驗證下宣稱它是主因**。

### 🔴 H7（中｜**真實 bug**｜loop 8 發現）`two_phase` 30° 與分組 45° 門檻不一致 → 相位空轉、吞吐砍半
- **證據（loop 8，跑 signals.json+graphml）**：**160/4899（3.3%）** 個 two_phase 號誌節點，**所有進場邊都落在同一相位組** → 另一相位（45s）**完全沒車、空轉**。
- **根因**：`build_signals.py:104` `two_phase = any(_circ_dist_180(a, ref_axis) > 30.0)`（**30°**）；但 `signals.py` 分組用 `_GROUP_HALF_WIDTH = 45`（**45°**）。approach 落在 30–45° → 被判 two_phase，分組時卻仍歸 group 0 → group 1 無車。
- **後果**：這 160 個節點，實際有車的 group 0 **每 90s 只綠 45s**（另 45s 空綠給沒車的 group 1）→ **吞吐被無謂砍半** → 若位於忙碌走廊（如北外環）會直接惡化回堵。
- **修法（未改，符合「先不修改」）**：兩處門檻對齊（都用 45°），或把 `two_phase` 改為「實際有 approach 落入兩個不同 group」才成立 → 全無車相位即不會產生。**屬真實可修 bug，非建模選擇。**
- **影響量化（loop 9）**：160 個中 **70 個最大車道 ≥2（多車道主幹道）**、90 個為單車道支道。多車道那 70 個才是實質吞吐損失（值得修）。
- **與症狀的關聯（loop 9）**：**距球場 2km 內僅 2 個 H7 節點、且皆 `tertiary` 次要道路（非北外環）** → **H7 並非北外環症狀的成因**；它是**獨立的全網背景 bug**。


### ✅❌ H3（loop 3 **實證推翻**）號誌相位軸 `ax=axes[0]` 任意 → 原以為會讓主幹道塞
- **loop 2 主張**：`ref_axis = axes[0]`（任意第一條邊）會把主幹道拆相/分到不利相位 → 主幹道塞。
- **loop 3 實證（4899 個 two-phase 號誌跑 signals.json+graphml）**：
  - **同 `bearing%180` → 同組 = 11970/11972 ≈ 1.0** → **直行道路兩對向必然同組、不會被拆相**（grouping 用 `bearing%180`，去向相反但同軸）。H3 的「拆相」**證偽**。
  - 主幹道落 group0/group1 ≈ 2549/2350（各半），**兩組皆 45s 綠 → ax 任意選不影響主幹道綠燈長度**。
  - 僅 ~4%（196/4899）節點主幹道在 ±45° 邊界（分組敏感）。
- **結論：H3 不成立**（loop 2 高估）。ax 任意**不會**讓主幹道少拿綠燈或被拆相。
- 附帶仍記錄：`two_phase` 用 30°、分組用 45° 門檻不一致（極次要，影響 <4% 邊界節點）。

### 🟠 H5（中｜真實因素｜loop 3 新增，loop 10 現場確認）固定 45/45 等分綠燈 → 過飽和主幹道只拿 50% 綠
- **機制**：號誌兩相位各 45s（cycle 90s），主幹道每 90s 只綠 45s = **50% 飽和流量**。北外環朝球場需求極高，若需求 > 50% 飽和 → **永遠排不完**。現實幹道通常給更多綠（60–70%）。
- **loop 10 現場確認**：球場 2.5km 內含多車道的 two-phase 號誌 **69 個**；抽樣顯示周邊為 **residential/tertiary 地方街道**，多車道路與支道 **45/45 平分綠燈** → 多車道路只拿 50% 綠（H5 在症狀現場成立）。
- **完整瓶頸鏈**：北外環（高容量環道）→ 灌入球場周邊「低容量地方街道網 + 50% 綠燈」→ **容量陡降 + 綠燈砍半 → 瓶頸 → 回堵爬上北外環**。屬真實「環道→地方路」轉換瓶頸。
- **性質**：非 bug，是**固定定時、等分綠燈 + 容量陡降**的真實限制。
- **緩解（未改）**：給主幹道相位更長綠燈（非等分）；或感應式號誌。屬介入/校準，非修錯。

### 🟢 H1（低｜降級｜loop 2 修正）`merge_priority` 全網平權 = 1
- **loop 2 修正**：UXsim 文件只說預設 1、**無「應設為車道數」的官方慣例**，UXsim 範例也未這樣設 → 專案**未違反慣例**。且在**號誌路口**綠燈為主控，`merge_priority` 主要在**無號誌匯流**生效 → 對「此號誌路口症狀」關聯性**不高**。由「中」降為「低」，列為可選建模改善（非 bug），不再視為主嫌。

### 🟢 H2（預期，非 bug）漏斗 / spillback（地理性需求集中）
- 事件車終點＝球場「抵達圈」內節點（`_assign_arrival_node` K-nearest，預設 5 個閘門、穩定 hash 分流）。

- 真實成因＝**北外環是高需求方向的主動脈、承載大份額** + H5 過飽和 + spillback。屬真實匯聚；解法＝多閘門/拓窄口/給幹道更多綠（非 bug）。

### 🟡 H6（低｜可調非 bug｜loop 4 新增）`arrival_radius_m=600` 偏小 → 加劇終點前集中
- 生效值 **600m → 僅 51 抵達節點**；R=1200→120、R=2000→275。半徑越小，車越往球場核心擠才算抵達 → 終點前回堵越重。

### 🟡 H3（待查｜號誌）斜交路口的 ±45° 軸相位分組是否誤判
- 北外環是**斜向**道路；號誌相位組由「進場方位角與該路口參考軸 `ax` 夾角 ≤45°」決定。斜交+複雜交流道可能讓直行主流被分到**綠燈較不利**的相位，或與支道同相而被稀釋。
- **待驗（未改）**：取該路口 `ax`、各進場 bearing、相位組，確認直行是否拿到足額綠燈。
